## MVP 1 Implementation Boundary

The receipt work is split into two explicit boundaries:

- **Local S1–S8:** provider-neutral OCR may use deterministic mocks, synthetic files, and local fixtures; no real receipts, live providers, or installed OCR binaries are required.
- **Receipt release:** `receipt-mvp` must run configured local Tesseract/OpenCV on synthetic image/PDF fixtures in the release-like web/worker image and persist extraction/normalized state in PostgreSQL. Record approved accuracy/review thresholds. Mocks are required for deterministic unit tests but cannot certify production. Real PDF promotion also requires an approved fail-closed scanner in the same candidate; synthetic PDF tests may mock it.

Google Document AI remains outside both boundaries until its separate privacy, region, cost, and provider approvals are recorded.

## Python Implementation Baseline
- Minimum Python: 3.12; declare runtime/dependency bounds in `pyproject.toml` and commit a reproducible lock.
- Docker application runtime: `python:3.14-slim-trixie`, which follows the latest stable CPython 3.14 patch published in the official image. As of 2026-10-01 it resolves to Python 3.14.7; upstream Python 3.14.8 is released, but the official Docker tag has not caught up. Keep the 3.14 minor line fixed and let the patch tag advance. Project compatibility remains Python 3.12 until a separate support-floor decision is made. The production runtime target excludes test sources and developer tools; use the Dockerfile `test` target for containerized tests.
- Current local service images: PostgreSQL `18.6-trixie`, Redis `8.10.2-trixie`, and uv `0.12.21` (latest releases observed 2026-10-01). Compose pins PostgreSQL/Redis patch and distro tags; refresh this inventory when infrastructure updates are requested.
- Use FastAPI, Pydantic 2, SQLAlchemy 2 sync sessions, Psycopg 3, Alembic, Celery, pytest. DB handlers are sync `def`; each request/task owns its session and transaction.
- Define schemas with backend-neutral SQLAlchemy models and change them only through reviewed, version-controlled Alembic migrations. Every table, column, index, constraint, or type change must have a migration; do not make untracked manual DDL changes or use `Base.metadata.create_all()` as a schema-management path. Test fresh, prior-revision, data-preserving upgrade, guarded downgrade, and replay paths against PostgreSQL. All database fixtures apply migrations on disposable PostgreSQL databases; pure unit tests use no database. Alembic and the application share connection configuration.
- Use Python `Decimal`/PostgreSQL `NUMERIC`, never floats, for money/fractional quantities; define currency scale/rounding at I/O boundaries.
- Run Ruff and mypy in CI; share Pydantic/API schemas without importing ORM models into templates. Pin the local OCR tools and external Square and Meta SDK/API versions; pin Google SDK/API versions if that future provider is enabled.
- Organize `src/mbs/` into bounded-context services, ORM models, Pydantic schemas, routers, Celery tasks, and provider adapters. APIs/workers share services; templates never access the DB directly.

## Cross-cutting rules (apply to every capability)
- Database: apply the PostgreSQL contract to all MVPs/capabilities; historical file-DB evidence cannot pass current gates.
- Schema: define changes in SQLAlchemy models and reviewed, versioned Alembic migrations. No manual/untracked DDL or `create_all()`; fixtures/profiles apply migrations.
- Browser tests: changed workflows require Python Playwright in the MVP profile, accessible selectors, headless Chromium in CI, desktop/mobile coverage, and recorded browser/version/viewports.
- Responsive UI: use responsive CSS/progressive enhancement in the selected stack; provide phone-usable and purpose-built desktop layouts. No user-agent-only detection or separate apps.
- Auth: server sessions use `Secure`, `HttpOnly`, `SameSite=Lax` cookies and shared CSRF on every state-changing cookie request, including JSON/uploads. Keep JWTs disabled until needed; then short-lived (D-14). Share user/auth services for login, revocation, reset, bootstrap, and roles; reset/recovery revokes sessions. Never store tokens in browser local storage.
- Product identity: always key sellable products by Square **Variation ID**, never by product name alone.
- Store identity: auto-create canonical stores from imported order/receipt text; never accept free-text purchase stores. Retain each spelling as an exact normalized alias. Display names may change; audited merges re-point aliases/receipts, splits are forward-only. Neither rewrites raw source text or accepted `Receipt_ID` store text.
- Purchased-item identity: canonical store + merchant ID/SKU, never description/common name; each store item maps to one canonical item. Store-observed items retain ≥1 store item; setup-created items may start with none. Square Variation IDs identify sellable products, not purchased items (D-52): recipe-made products use effective recipes; direct resale may link one canonical item. Finished stock/sales key by Variation ID; purchased costs/stock by canonical item. Descriptions alone never merge/split.
- Item naming: canonical/store items may have user-entered common names. Display the order description until set; common names are display/search metadata, never identity/match keys, and never overwrite raw descriptions.
- Shelf life: require and remember per-item `days`/`weeks`/`months`/`never` before import/save (`NOT NULL`; no checkbox/default). Reject missing values before item/stock creation. Lot `Perishable By` = acquisition + item shelf life; recipe lots use required output life from production time. Startup/interval expiry posts waste once per lot; weekly close reconciles, not blanket-wastes perishables.
- Time: store UTC instants; require ADMIN-set IANA `business_timezone` before dated sales or weekly/expiry jobs. Derive business dates, Monday boundaries, hours, and expiry there; display browser-local times with timezone labels. Test DST and distinguish display/business time.
- Dates: use full ISO `YYYY-MM-DD` business dates only; store date-times as UTC plus interpretation timezone. Reject month/day-only dates.
- Effective periods: use inclusive full-date bounds and resolve by event date. Preserve historical records/snapshots. Expand recurring patterns to year-specific dates and validate gaps/overlaps before use.
- Date ownership: market visits, operating hours, sales, purchases, expenses, inventory periods, route rates, product costs, settings, and tax workpapers must retain the applicable calendar year. Tax year and market/business date are separate fields and must not be inferred from a month or week alone.
- Source of truth: Square owns sales, tenders, payments, refunds, settlements; MBS owns attribution, inventory, costs, expenses, reconciliation; users/preparers own corrections, exceptions, tax classes, overrides. Never silently replace provider facts.
- Square API is read-only: one fail-closed allowlist adapter, least-privilege credentials, and a negative test proving forbidden mutations send no request. MBS sync writes MBS only; change Square externally.
- Market attribution: a Square sale is assigned to a market only when its mapped Square Location, complete local business date, dated market visit, and effective local operating-hours period all resolve. Sales on closed dates, outside hours, at an ambiguous/shared location, or without a matching visit remain visible exceptions until an authorized override records the reason and approver.
- Corrections: provider facts, accepted sales, costs, schedules, and tax exports are immutable. Append linked reversals/adjustments/replacements with actor, time, reason, lineage; never rewrite originals or reports. Before receipt approval, D-45 permits normalized edits only with immutable before/after events and snapshot versions; raw OCR remains immutable.
- Integration evidence: check runtime behavior only after testing the real FastAPI-startup, Celery-task, or CLI entry point. Unit tests prove components, not delivery. Mark schema unused until it has a writer and reader.
- Private data: keep real receipts/exports/expected results in ignored local paths; never commit them. Before commit/push, `git ls-files receipts/` must be empty; purge accidental commits before push.
- Calendar: configure IANA timezone, week start, and tax year (D-65). Market holidays/calendars are Capability 5 dated market data, not global settings. `tax_year` is only a screen default; assign records by business date. Overnight/exceptional sessions need explicit business-date rules, never UTC inference.
- Price authority: Square Catalog is authoritative for Square product identity and standard Square sale prices; accepted Square Orders own actual sale amounts. MBS retains reviewed effective-dated cost and margin data but does not apply market-session price overrides (D-02).
- Initial scope assumptions: the first production release supports one legal entity, one business, one Square account, one operating currency (USD), and multiple authorized ADMIN/MANAGER/VIEWER users. Keep business, legal-entity, currency, and provider-account identifiers on records so a future multi-business design does not require re-keying history.
- Operational readiness: before MVP 2 production, test Catalog-only sync, setup exceptions, backup/restore, and device/browser recovery. MVP 2 may show Catalog pending/failed/staged/setup-required, never imply Orders/Payments imported/settled. Sales states start in MVP 3.
- Test isolation: rows with `Test Record = Yes` must never appear in production aggregations/dashboards/reports.
- MVP sequence: MVP 2 stages Catalog, market/visit setup, Direct Sell stock, products/recipes/costs, and one balance reader; no Orders/Payments. MVP 3 stages/accepts them, keeping unresolved lines outside the ledger. Later records feed inventory/COGS, rankings, dashboards, tests. Receipt capture remains MVP 1; tax workpapers use approved, source-linked year snapshots.
- Market-day: Square alone owns sales/tenders; no parallel ledger or cash count. Targets add no stock. Approved receipt lines add purchases; confirmed made quantities add recipe products; accepted Square quantities subtract once by Variation ID (D-53). Production requires Square connectivity, three roles, settlement visibility, duplicate/pending recovery tests.
- Domain writes use transactions and unique source-event keys. Receipt approval and production (including stock/remainder) commit atomically. External calls use persisted workflows/reconciliation; never claim exactly-once provider effects.

## PostgreSQL Contract (All Stages)

D-77 changes deployment/validation, not domain logic. PostgreSQL 18.6 is sole runtime/test DB; no file-DB fallback/fixtures or silent service skips.

- Config: `DATABASE_URL` overrides split `DATABASE_*` fields. Use `URL.create` for credentials/split fields, `make_url` for full URLs; `postgresql://` selects Psycopg 3. Explicit Alembic Config URL wins; escape `%` as `%%`. Never log secrets.
- Portable core: keep generic engines/sessions/queries, `Numeric`, `Boolean`, TZ-aware `DateTime`, and `JSON` with PostgreSQL `JSONB` variant. Backend-specific casts/sequences/indexes/snapshot dump belong in migrations/infrastructure.
- Other engines are not certified by changing URLs. Filtered uniqueness, casefolding, locks, DDL/isolation, timezones, and backups need equivalent adapters/tests; removing migration branches removes compatibility. SQLAlchemy support ≠ app support.
- Schema: ORM metadata matches migrated types/constraints; keep revisions stable. Revision 0020 supports 128-char IDs; 0026 fixes store-hold JSONB. Never rename revisions, stamp failures, reset app volumes; data-losing downgrades must refuse and use coordinated restore.
- Transactions: each request/task owns a session and commits/rolls back explicitly; never share sessions across threads/processes. Preserve `autoflush=False`/`expire_on_commit=False`, flush dependencies, use savepoints for recoverable uniqueness errors, and protect writes with parent locks/idempotency keys. Reset Celery child pools; use pre-ping/rollback-on-return.
- Data: bind values; use real booleans, Decimal/Numeric, UTC instants, full dates, deliberate lengths/nullability. Test rounding/overflow, FK order, NULLs, DST/effective dates, ordering, normalization.
- Test safety: `MBS_TEST_DATABASE_URL` may target only dedicated `mbs_test`/`mbs_migration_test` with DB-create rights. Create random isolated DBs/schemas; clean only owned resources; never use app/prod credentials. Focused: `docker compose run --rm test-dev pytest <tests> -q`; full: `docker compose run --rm test-dev`; candidate: unmounted `docker compose run --rm --build test`.
- Recovery: app/test images include PG18 clients. Dump/count one exported snapshot; quiesce writers/drain workers for DB+file backup/restore. Restore transactionally only to empty isolated targets, then verify counts/checksums. Timed RPO/RTO and restart drills are separate gates.
- Images: separate runtime/test; include Chromium/catalog/synthetic tools, never private receipts. Dev ports loop back. Production disables DB exposure, reload, source mounts, test services, and example passwords. Mounted edits need no test-dev rebuild; candidate image checks do.

## Cross-Capability Contracts

These contracts are authoritative for implementation slices. Capability files may add detail but must not redefine them silently.

| Contract | Authority and invariant |
|---|---|
| Identity and ownership | Square Variation ID is the sellable-product identity. A purchased line's identity is canonical store + store product identifier, resolved to one canonical item ID; store aliases, display names, and common names are presentation data only. Square provider facts belong to Capability 3 staging; accepted sales and reconciliation belong to Capability 14; market visits and schedules belong to Capability 5; inventory movements belong to Capability 6; market-day sessions use those services and never create parallel ledgers. |
| Store and item mapping | Stores are auto-created from imported order/receipt data and edited only through the store management service (display name, alias grouping, merge, forward-only split). Store items are auto-created per canonical store + store product identifier and mapped many-to-one onto canonical items through the item mapping service. Suggestions derived from common names or receipt descriptions are proposals requiring explicit confirmation; an unmapped store item stays visible for mapping, blocks posting, and never silently creates a second canonical item for an already-mapped product. Regrouping or remapping is effective-dated and audited, and never rewrites posted purchases, costs, or stock movements. |
| State and totals | Provider-staged, pending, accepted, import-exception, operationally-closed, and settlement-reconciled states must follow the approved transition table in [04-go-no-go.md](04-go-no-go.md). Only accepted business records affect sales, inventory, and tax totals; pending and exception amounts remain separately labelled. |
| Time and effective dates | Persist UTC instants plus the configured IANA `business_timezone`. Persist complete ISO business dates. Effective-dated records use inclusive full-date ranges, reject overlaps, and resolve historical records using the date of the event rather than current settings. |
| Corrections | Imported facts, accepted sales, costs, schedules, snapshots, and exports are immutable. Corrections append linked reversal, adjustment, replacement, or restatement records with actor, reason, timestamp, and source lineage. |
| Idempotency and transactions | Every domain write has a stable source-event/idempotency key and database uniqueness protection. A receipt approval, production confirmation, sale acceptance, or stock allocation commits all local effects atomically; external API calls use persisted workflow states and reconciliation rather than an exactly-once claim. |
| Receipt evidence and downstream posting | One reviewed order/receipt may have multiple original PDFs; an overlapping copy adds no purchase facts, while an approved supplement may add a separate occurrence of an already-seen merchant item. Store each source and raw extraction immutably, keep one canonical receipt with per-line provenance, and reconcile accepted line amounts to the printed item subtotal with tax separate. Only approved business line occurrences may create purchase, cost, stock, expense, asset, analytics, or tax facts; never key these effects by upload count, description, or merchant item number alone. Hold conflicting or incomplete evidence for review, and preserve historical effects through audited correction/reversal rather than replaying every source file. |
| Test isolation and evidence | `Test Record = Yes` rows are excluded from production aggregates. A plan checkbox is not complete until its focused test, runnable command, migration/profile evidence, and manifest row are verified against the actual repository, and any runtime claim is exercised through the real entry point. |
| Synthetic fixture realism | Synthetic data is mandatory for every committed fixture, seed, demo, and test, but it must not be arbitrary. When a fixture represents something the business actually receives — receipt headers and layouts, store spellings, abbreviated item descriptions, merchant item numbers, pack sizes and unit tokens, weighed lines, REF/TR# references, timestamp and tax/subtotal placement, multi-page or multi-file orders, card masking — model its **shape** on the real examples in the local untracked `receipts/` directory and their reviewed expected results, so tests exercise the formats the parser will really meet. Reproduce structure, vocabulary, and edge cases; invent the values. No real store name, item description, item number, reference, amount, date, card digit, image, or expected-result file is ever copied into the repository, a test, CI, a log, an export, or a chat message. A fixture is still synthetic only if nothing in it identifies a real purchase. |
