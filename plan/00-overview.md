The Blueprint DOCX and files in [support/](../support/) are reference materials only. This is a **planning document only** — no application code is implemented here.

## How to use this plan
- Each capability below has its own file under `plan/capabilities/`. Check the box at the top of a capability file only when **all** its features are checked.
- Each feature has its own checkbox. Check it only when all its implementation steps are checked.
- Steps marked **🧑‍💻 User Input Required** cannot be completed by the coding agent alone — they need an account, credential, purchase decision, or physical machine access from you. Each such step spells out exactly what to do, including links.
- Capability numbers identify functional areas; deploy in the staged order defined by [01-mvp-roadmap.md](01-mvp-roadmap.md), not by capability number alone.
- Complete the [implementation-readiness gate](02-implementation-readiness.md) before using real business data or approving an MVP 1 production release. Local development with synthetic data and mocked providers may proceed while the gate is open.
- Use [03-current-slice.md](03-current-slice.md) as the single source for the next bounded implementation task; do not infer task priority from capability numbering or unchecked boxes alone.
- Use [mvp-slice-specifications.md](mvp-slice-specifications.md) as the approved slice contract for MVP 2-8. Future MVP prose is not an implementation instruction until its row is copied into `03-current-slice.md` with evidence links.
- The source artifacts are evidence and design guides, not permission to override this plan's confirmed decisions or business rules. In particular, `support/Devin_MBS_v3_3_Prompt.txt` and its DOCX counterpart are historical project prompts; their Java/Spring/React/Kubernetes stack is superseded by the Python-native decisions below. The source workbook, blueprint, and their formulas remain reference material subject to the precedence in the readiness gate.
- [test-case-manifest.csv](test-case-manifest.csv) is the required traceability artifact. Its presence does not mean its case mappings or release evidence are complete.

## MVP 1 Implementation Boundary

The receipt work is split into two explicit boundaries:

- **Local development slices S1-S8:** provider-neutral OCR contracts may use deterministic mocked extraction, synthetic files, and local database fixtures. These slices may be implemented and validated without real receipt data, live providers, or installed OCR binaries.
- **Receipt MVP release:** the `receipt-mvp` profile must run the configured local Tesseract + OpenCV adapter against synthetic image/PDF fixtures in the release-like web/worker image, persist the extraction and normalized receipt state in PostgreSQL, and record the approved OCR accuracy/review thresholds. A mocked provider test is necessary for deterministic unit coverage but is not sufficient evidence for MVP 1 production promotion. Because MVP 1 promises real PDF upload, its production gate also requires an approved fail-closed PDF scanner in the same release candidate; synthetic local PDF tests may use a mocked scanner.

Google Document AI remains outside both boundaries until its separate privacy, region, cost, and provider approvals are recorded.

## Python Implementation Baseline
- Minimum Python version: 3.12. Declare runtime and dependency constraints in `pyproject.toml`; commit a reproducible dependency lock file.
- Use FastAPI, Pydantic 2, SQLAlchemy 2 synchronous sessions with Psycopg 3, Alembic, Celery, and pytest. Database-backed FastAPI handlers are synchronous `def` routes so blocking SQL is not run inside the event loop; give each request/task its own session and transaction.
- Define PostgreSQL schemas with SQLAlchemy models and change them only through reviewed, version-controlled Alembic migrations. Every table, column, index, constraint, or type change must have a migration; do not make untracked manual DDL changes or use `Base.metadata.create_all()` as a schema-management path. Review autogenerated revisions and test migrations against both a fresh database and the prior schema; test fixtures must apply migrations too. SQLite fixtures are acceptable for fast unit tests, but a migration step is complete only after the full chain upgrades and downgrades against PostgreSQL, and Alembic reads the same `DATABASE_URL` as the application.
- Represent money and fractional quantities with Python `Decimal` and PostgreSQL `NUMERIC`, never binary floats; define currency scale and rounding at explicit input/output boundaries.
- Run Ruff and mypy in CI; share Pydantic/API schemas without importing ORM models into templates. Pin the local OCR tools and external Square and Meta SDK/API versions; pin Google SDK/API versions if that future provider is enabled.
- Organize the application as `src/mbs/` with bounded-context services, SQLAlchemy models, Pydantic schemas, FastAPI routers, Celery tasks, and provider adapters kept in separate modules. APIs and workers call the same domain services; templates never access the database directly.

## Cross-cutting rules (apply to every capability)
- Database schema lifecycle: every capability and MVP that creates or changes PostgreSQL schema must define it with SQLAlchemy models and ship a reviewed, version-controlled Alembic migration. No untracked/manual DDL or `Base.metadata.create_all()` as a schema-management path; automated fixtures and release profiles apply the migration chain.
- Browser UI verification: every capability that adds or changes browser UI must include Python Playwright end-to-end tests in its MVP-specific test profile. Cover the changed workflows and representative mobile and desktop layouts; use accessible names/roles for robust selectors, run headless Chromium in CI, and record the browser/version and viewport results.
- Device-appropriate web UI: every screen must adapt to the available viewport and input capabilities, presenting a usable mobile layout on phones and a purpose-built desktop layout in computer browsers. Desktop views must use the available space for efficient navigation and work, not merely display a narrow mobile screen on a large monitor. Use responsive CSS/media queries and progressive enhancement within the selected Jinja2/HTMX/Alpine.js/Tailwind stack; do not rely solely on user-agent detection or require a separate mobile/desktop application.
- Auth: server-side browser sessions use `Secure`, `HttpOnly`, `SameSite=Lax` cookies plus CSRF protection on every state-changing cookie-authenticated request, including JSON and upload routes; enforce CSRF through one shared dependency rather than per-route code. Bearer JWTs stay disabled until a machine client needs them (D-14); when enabled they are short-lived. Login, logout/revocation, password reset, first-admin bootstrap, and role checks share one user/authorization service; a password reset or recovery revokes the user's existing sessions. Never store auth tokens in browser local storage.
- Product identity: always key sellable products by Square **Variation ID**, never by product name alone.
- Store identity: every purchase source is a canonical store record. Stores are created automatically from the store value read on an imported order/receipt — never typed as free text on a purchase line — and each distinct source spelling is retained as a store alias resolving by exact normalized key to one canonical store. A user may change a store's display name and group multiple alias spellings into a single canonical store; an audited merge re-points aliases and receipts, a split is forward-only, and neither rewrites the raw store text on a source document or the store component of an accepted `Receipt_ID`.
- Purchased-item identity: the canonical purchase store plus its own product identifier (merchant item number/SKU) identifies a purchased line, never the description or common name. Each store item resolves to exactly one canonical item ID. A canonical item first observed from a store always keeps at least one store item; a setup-created item may have none until its first purchase. Square Variation IDs identify sellable products, not purchase-store items (D-52): a recipe-made variation links to an effective recipe of canonical purchased ingredients/supplies; direct resale may link to one canonical purchased item. Finished-product sales/stock key by Variation ID; purchased-item costs/stock key by canonical item ID. Matching descriptions alone never merge or split items.
- Item naming: each canonical item and each store item may carry a user-entered common name because receipt descriptions are abbreviated. The displayed name defaults to the name read from the order until a common name is recorded; a common name is display/search metadata and never becomes an identity, match key, or a change to the stored raw description.
- Shelf life: every stocked product, ingredient, and supply carries a required Shelf Life (`days`, `weeks`, `months`, or `never`) before import or persistence and is remembered as that item's default; the database column is `NOT NULL`, and there is no perishable checkbox or system-supplied default duration. An import or item-creation request without Shelf Life is rejected before an item or stock row is saved. Each lot's `Perishable By` is its acquisition instant plus that shelf life, except recipe-produced lots, which use the recipe's mandatory output shelf life from the production timestamp. A background expiry job runs at startup and on an interval to post waste once per expired lot; weekly close reconciles rather than wasting perishables as a class.
- Store instants in UTC and require an admin-configured IANA `business_timezone` before importing dated sales or scheduling weekly/expiry jobs. Derive market business dates, Monday boundaries, market hours, and expiry calculations in that timezone; display date-times to each user in the browser's timezone with a visible timezone label. Test daylight-saving transitions and distinguish browser display time from business date/time.
- Date policy: every persisted or user-entered business date is a full Gregorian calendar date in ISO 8601 `YYYY-MM-DD` form, including the year; every date-time stores an instant in UTC plus the source/business timezone used for interpretation. Never store or accept month/day-only values such as `July 1` or `08/31` for business records.
- Multi-year policy: effective-dated records use inclusive full-date `start_date` and `end_date` values, may span multiple calendar years, and are selected using the record's complete date. Historical records and their resolved effective-period snapshots are immutable. A recurring annual pattern is only a configuration convenience; before it affects a business record it must resolve to explicit year-specific dates, with overlap and gap validation for each affected year.
- Date ownership: market visits, operating hours, sales, purchases, expenses, inventory periods, route rates, product costs, settings, and tax workpapers must retain the applicable calendar year. Tax year and market/business date are separate fields and must not be inferred from a month or week alone.
- Source-of-truth matrix: Square owns every actual sale, tender, completed transaction, payment, refund, and provider settlement fact; MBS owns market attribution, inventory movements, product/recipe costs, expenses, and reconciliation state; the user or authorized tax preparer owns corrections, exceptions, tax classifications, and approved overrides. Provider facts are never silently replaced by MBS-derived values.
- Square API is strictly read-only for MBS across all releases: no application path may attempt to create, update, cancel, refund, or delete Square data. Use a single fail-closed provider adapter with an explicit allowlist of read-only operations (including specifically approved POST-based searches), credentials limited to required read permissions, and a blocking negative test proving mutating operations produce no outbound request. Local MBS sync and reconciliation may write only MBS records; changes in Square are made outside this application.
- Market attribution: a Square sale is assigned to a market only when its mapped Square Location, complete local business date, dated market visit, and effective local operating-hours period all resolve. Sales on closed dates, outside hours, at an ambiguous/shared location, or without a matching visit remain visible exceptions until an authorized override records the reason and approver.
- Corrections and restatements: imported provider facts, accepted sales, historical costs, market schedules, and exported tax snapshots are immutable. Corrections append linked reversal, adjustment, or replacement records with actor, timestamp, reason, and source lineage; they never rewrite the original fact or silently change prior reports. Receipt review before approval is the one bounded exception (D-45): normalized rows may be edited, but each edit appends an immutable correction event with reason and before/after values and versions the canonical snapshot; raw OCR evidence is never edited.
- Integration evidence: a plan step that describes runtime behavior (an endpoint, pipeline stage, job, or rule that affects processing) is checked only when a test exercises it through the real entry point — the FastAPI app with its startup wiring, a dispatched Celery task, or the CLI. Service-level unit tests are recorded as component evidence and must not be described as delivered behavior. Schema added for a later consumer is labelled as unused until it has a writer and reader.
- Private data: real receipts, exports, and derived expected-result files stay in git-ignored local paths and must never be committed. `.gitignore` does not untrack a file already committed, so `git ls-files receipts/` must return nothing before any commit or push; any accidental commit is purged from history before it is pushed.
- Calendar policy: store the configured IANA business timezone, week-start day, and tax year as explicit settings (D-65). Market-specific calendar and holiday exceptions are **not** settings: they are Capability 5 per-market dated master data, because a global setting cannot express one market closed while another trades the same day. A tax year and a market/business date are separate concepts, and the `tax_year` setting is a screen default only — which records belong to a tax year is always derived from each record's own business date. Overnight or exceptional market sessions require an explicit business-date rule rather than inference from UTC.
- Price authority: Square Catalog is authoritative for Square product identity and standard Square sale prices; accepted Square Orders own actual sale amounts. MBS retains reviewed effective-dated cost and margin data but does not apply market-session price overrides (D-02).
- Initial scope assumptions: the first production release supports one legal entity, one business, one Square account, one operating currency (USD), and multiple authorized ADMIN/MANAGER/VIEWER users. Keep business, legal-entity, currency, and provider-account identifiers on records so a future multi-business design does not require re-keying history.
- Operational readiness: before MVP 2 production, define and test Catalog-only synchronization, setup-exception visibility, backup/restore, and device/browser recovery. The MVP 2 UI may show Catalog sync pending, failed, staged, or setup-required states but must not imply that Orders/Payments have been imported or settled. Sale import, acceptance, and settlement states first appear with MVP 3.
- Test isolation: rows with `Test Record = Yes` must never appear in production aggregations/dashboards/reports.
- MVP 2 is Catalog staging, market/location/dated-visit setup, receipt-backed Direct Sell stock, products, recipes, costing, and the single expected-inventory reader; it does not stage or accept Square Orders/Payments. MVP 3 activates Order/Payment staging and accepts passing order lines while keeping unresolved lines outside the accepted ledger. Thereafter, business-record and product/market updates feed inventory/COGS and rankings, then dashboards and testing. Receipt upload/OCR/storage remains the independent MVP 1 release. Tax workpapers use approved records and retain source lineage and a year-specific snapshot.
- Market-day operations use Square as the only sales and tender system and the shared inventory movement source; MBS must not create a parallel sales ledger or count cash. A planned shopping/production target never creates stock: reviewed receipt-line purchases add purchased items, user-confirmed made quantities add recipe-made finished products, and accepted Square line quantities subtract the corresponding Variation ID once (D-53). Production requires Square connectivity, the approved three-role model, settlement-status visibility, and recovery tests for duplicate or pending imports.
- Domain writes use database transactions and unique source-event/idempotency constraints. A receipt approval posts its linked business record atomically; a production confirmation commits its production event, stock movements, and fractional-waste remainder atomically. External provider calls use persisted workflow states and reconciliation; do not claim an external API side effect is exactly-once.

## Cross-Capability Contracts

These contracts are authoritative for implementation slices. Capability files may add detail but must not redefine them silently.

| Contract | Authority and invariant |
|---|---|
| Identity and ownership | Square Variation ID is the sellable-product identity. A purchased line's identity is canonical store + store product identifier, resolved to one canonical item ID; store aliases, display names, and common names are presentation data only. Square provider facts belong to Capability 3 staging; accepted sales and reconciliation belong to Capability 14; market visits and schedules belong to Capability 5; inventory movements belong to Capability 6; market-day sessions use those services and never create parallel ledgers. |
| Store and item mapping | Stores are auto-created from imported order/receipt data and edited only through the store management service (display name, alias grouping, merge, forward-only split). Store items are auto-created per canonical store + store product identifier and mapped many-to-one onto canonical items through the item mapping service. Suggestions derived from common names or receipt descriptions are proposals requiring explicit confirmation; an unmapped store item stays visible for mapping, blocks posting, and never silently creates a second canonical item for an already-mapped product. Regrouping or remapping is effective-dated and audited, and never rewrites posted purchases, costs, or stock movements. |
| State and totals | Provider-staged, pending, accepted, import-exception, operationally-closed, and settlement-reconciled states must follow the approved transition table in [04-go-no-go.md](04-go-no-go.md). Only accepted business records affect sales, inventory, and tax totals; pending and exception amounts remain separately labelled. |
| Time and effective dates | Persist UTC instants plus the configured IANA `business_timezone`. Persist complete ISO business dates. Effective-dated records use inclusive full-date ranges, reject overlaps, and resolve historical records using the date of the event rather than current settings. |
| Corrections | Imported facts, accepted sales, costs, schedules, snapshots, and exports are immutable. Corrections append linked reversal, adjustment, replacement, or restatement records with actor, reason, timestamp, and source lineage. |
| Idempotency and transactions | Every domain write has a stable source-event/idempotency key and database uniqueness protection. A receipt approval, production confirmation, sale acceptance, or stock allocation commits all local effects atomically; external API calls use persisted workflow states and reconciliation rather than an exactly-once claim. |
| Receipt evidence and downstream posting | One reviewed order/receipt may have multiple original PDFs; an overlapping copy adds no purchase facts, while an approved supplement may add a separate occurrence of an already-seen merchant item. Store each source and raw extraction immutably, keep one canonical receipt with per-line provenance, and reconcile accepted line amounts to the printed item subtotal with tax separate. Only approved business line occurrences may create purchase, cost, stock, expense, asset, analytics, or tax facts; never key these effects by upload count, description, or merchant item number alone. Hold conflicting or incomplete evidence for review, and preserve historical effects through audited correction/reversal rather than replaying every source file. |
| Test isolation and evidence | `Test Record = Yes` rows are excluded from production aggregates. A plan checkbox is not complete until its focused test, runnable command, migration/profile evidence, and manifest row are verified against the actual repository, and any runtime claim is exercised through the real entry point. |
| Synthetic fixture realism | Synthetic data is mandatory for every committed fixture, seed, demo, and test, but it must not be arbitrary. When a fixture represents something the business actually receives — receipt headers and layouts, store spellings, abbreviated item descriptions, merchant item numbers, pack sizes and unit tokens, weighed lines, REF/TR# references, timestamp and tax/subtotal placement, multi-page or multi-file orders, card masking — model its **shape** on the real examples in the local untracked `receipts/` directory and their reviewed expected results, so tests exercise the formats the parser will really meet. Reproduce structure, vocabulary, and edge cases; invent the values. No real store name, item description, item number, reference, amount, date, card digit, image, or expected-result file is ever copied into the repository, a test, CI, a log, an export, or a chat message. A fixture is still synthetic only if nothing in it identifies a real purchase. |
