# Capability 4: Product, Recipe & Costing Management

Database support: PostgreSQL only; follow [D-77's shared contract](../00-overview.md#postgresql-contract-all-stages).
- [ ] Test Numeric scale/rounding/overflow, effective recipe/cost gaps and overlap races, NULL/blocked results, generic Decimal calculations, and preserved item/image lineage during upgrades.

- [ ] **Capability complete** (all features below checked)

Bounded context: `mbs/products/` (blueprint §3.1 #1, Modules 1–4). Product catalog, recipes, ingredient cost history, product cost engine, and derived readiness status.

Purchased ingredients and supplies resolve through Capability 2 canonical `item_id`s and purchased store items. A Square-sold product is keyed by Variation ID: recipe-made outputs use an effective recipe of those canonical inputs; directly resold products may link to a canonical purchased item (D-52). Vendor/store fields on purchases and costs reference canonical purchase `store_id`, not typed store text; common names are display metadata only.

## Feature 4.1 — Product Master

- [ ] `tblProductSetup` model, keyed by Square **Variation ID** (never product name) — Governance Rule 1.
- [ ] Keep the Variation ID as the finished-product identity. An effective recipe links recipe-made products to purchased input `item_id`s; a direct-resale product may instead link to one purchased canonical `item_id`, never a Square store item. Reject conflicting simultaneous sourcing modes and preserve the effective mapping used by historical production, costs, and sales (D-52). Keep customer-facing name, common name, and store-printed descriptions separate from identity.
- [ ] Expose `Direct Sell` as an explicit product setup choice for a Square variation linked to one canonical purchased item. Its approved receipt line supplies actual purchased quantity/cost (for example one 24-pack normalized to 24 bottled waters); market load confirmation selects only the quantity brought from that stock (for example 6), not a new purchase or production event. Reject an unmapped item, unreviewed pack conversion, or insufficient receipt-backed stock rather than inventing cost or units (D-55).
- [ ] Before creating a Variation-ID restock from a receipt line, check the inverse mapping: if the same canonical purchased item links to multiple active Direct Sell variations, hold the receipt routing record and create no stock event for any of them. A shared-item allocation requires the separate owner-approved conserved-quantity contract in the MVP 2 readiness gate; neither Variation ID may independently claim the whole purchased quantity (DS-001).
- [ ] In MVP 2, create a sellable product record for each Square Variation ID; derive its reviewed effective-dated cost only when persisted receipt-backed input costs and a valid recipe or direct-item link exist. An incomplete product remains SETUP REQUIRED or returns a typed blocked cost and cannot be accepted in MVP 3 (D-63/D-71). A `Direct Sell` record links to its MVP 1 canonical purchased item before slice 2.2a posts receipt-backed stock; slice 2.5 extends that link with full conversion/costing history rather than re-keying it. No provisional typed-in cost is created.
- [ ] Under D-63 recipes and costs exist before the first sale, so no provisional finished lot is created on the build path. If such a lot ever exists, leave it at its original reviewed cost, product Shelf Life, remaining quantity, and Square history; only future batches use a newly effective recipe. Provide MANAGER+ review of D-56 historical input-use exceptions with source links, actor/time/reason, and an audited resolution or supported separate adjustment; insufficient evidence keeps the exception open and affected calculations blocked. Never synthesize past input movements or mislabel a provisional COGS as recipe-derived (PR-001, contingency only).
- [ ] Store a required, database `NOT NULL` Shelf Life on each inventory-tracked product as `shelf_life_value` + `shelf_life_unit` (`days`, `weeks`, `months`, or `never`). Require the value before importing or creating the product; reject the request before persistence when it is missing. There is no `is_perishable` checkbox: an item is perishable when its unit is not `never`. Never infer Shelf Life from merchandise category, recipe, or a default number of days.
- [ ] Let a MANAGER set `waste_at_plan_end` on an effective recipe version only, separately from its mandatory output Shelf Life. Capture the recipe version used by each produced lot; changing the checkbox affects future production, never past lots or `Perishable By`. A fruit-cup recipe may have it checked; a longer-lived candy recipe may leave it unchecked. Direct Sell products have no recipe checkbox and follow their canonical item's Shelf Life (D-54).
- [ ] Remember the confirmed Shelf Life on the item master and reuse it as the default for every future lot of that item. Changing it is an audited master-data edit that recomputes `Perishable By` for open lots from each lot's acquisition instant; closed periods and already-posted waste are corrected only through Capability 6 restatement.
- [ ] Store Target Stock Quantity (the intended replenishment/order quantity) and optional Product URL per Variation ID; use the product's inventory unit. When entering a purchase, offer its quantity as the suggested target and let the user confirm/change it.
- [ ] Do not capture physical opening counts. Market Planning supplies a target only; approved receipt purchases add canonical purchased stock, confirmed made quantities add finished Variation-ID stock, and accepted Square line quantities reduce finished stock. Transfers, dispositions, and expiry update expected inventory without double-counting a plan (D-53). Only `never` items permit an audited expected-inventory override.
- [ ] Migrate MVP 1 minimal ingredient/recipe and receipt-item links with stable identities into the MVP 2 product/recipe models. The MVP 1 minimal Ingredient record and the canonical `item_id` are not parallel identities: each minimal Ingredient carries its `item_id` from creation, and MVP 2 expands that same record rather than creating a second master. Preserve each MVP 1 routing-record ID, state, source-event key, and any consuming-fact link so pending, posted, and reversed records are never reprocessed as new purchases. The migration must be replay-safe, preserve every receipt/item link, mapping, audit identity, and historical cost row, and support tested rollback recovery.
- [ ] Product status derivation under D-28/D-52: READY requires effective cost plus a complete effective recipe for recipe-made products, or effective cost plus a valid canonical purchased-item link for direct resale. CONFIGURE PRODUCT when cost and sourcing are both missing; SETUP REQUIRED when exactly one is missing, naming `Recipe or Direct Item` or `Cost` as appropriate. MVP 2 accepts no Square order line; MVP 3 accepts only a READY product with its real recipe-derived or direct-item cost.
- [ ] Slice 2.3 may record recipe-made sourcing as pending but must not create an effective recipe; slice 2.4 validates and versions recipes, and only slice 2.5 wires persisted receipt-backed dated cost rows so either sourcing mode can become READY. Synthetic cost rows in slice 2.4 tests never make a persisted product READY.
- [ ] Store approved customer-facing product name, sale unit, display price, active/inactive status, and optional customer description separately from internal cost and margin fields. Do not expose internal costs in the market-day price list.
- [ ] Store reviewed allergen, ingredient, storage, best-by, batch/production-date, and preparation information when applicable; keep applicability and review status auditable and do not infer regulatory claims from OCR merchandise categories.
- [ ] `GET/POST /api/v1/products`, `GET/PUT /api/v1/products/{variation_id}` per blueprint §9.1.
- [ ] Handle products missing from Square catalog gracefully (flagged, not silently dropped).

## Feature 4.2 — Recipe Framework
- [ ] Feature complete
- [ ] `tblIngredients` + `tblRecipeMaster` + `tblRecipeIngredients` + `tblProductRecipeMapping`: ingredient master with stable Ingredient ID, a link to its canonical `item_id`, name, base unit, active status, and database `NOT NULL` Shelf Life value/unit required before import or creation; recipes link one-or-more ingredient rows with Quantity Per Item + Unit. Product-recipe mappings are effective-dated, allow at most one active recipe for a Variation ID on any date, reject overlapping periods, and preserve the recipe version used by historical production and costs. An ingredient's purchasable forms come from that item's store items; do not create a second ingredient because a store prints a different description.
- [ ] Require a database `NOT NULL` output Shelf Life on `tblRecipeMaster` (`output_shelf_life_value` + `output_shelf_life_unit`, `never` allowed) before the recipe can be saved. Reject recipe creation/import before persistence when it is missing. Produced lots always expire on the recipe duration measured from the production timestamp; it overrides the finished product's own Shelf Life and every component's standalone Shelf Life for components consumed into that lot, including packaging supplies. A supply marked `never` is wasted with the recipe lot when used in that lot; unused supply stock keeps its own Shelf Life. A recipe output Shelf Life edit is audited/effective-dated: recompute open lots from production time under D-35, while posted waste, closed periods, and previously exported snapshots change only through a linked restatement, never silent mutation.
- [ ] Store a `Waste Percentage` (0–100%, default 0%) on each recipe input. Add `tblRecipeSupplies` rows for stocked supplies (for example, one cup per finished item) with quantity, unit, and waste percentage so packaging waste is attributable to its stock item; enforce the 0–100 bound in the database and service layer.
- [ ] Calculate expected input waste as `prepared quantity × quantity per item × (Waste Percentage / 100)`. For discrete whole-unit stock such as cups, retain the fractional remainder by recipe input across production events and post a waste movement only when accumulated expected waste reaches a whole inventory unit; do not round each batch up. For stock units that support fractional quantities, post the exact waste quantity.
- [ ] In MVP 2, test fractional-waste calculation over synthetic sequences without posting production. MVP 4's shared production service persists the remainder across batches/week boundaries and reverses or recalculates it on audited corrections; unconfirmed plans never accrue or post waste (PC-001).
- [ ] Recipe completeness rule: at least one ingredient row with valid Quantity Per Item and matching Unit, plus a recorded output shelf life.
- [ ] Recipe-derived shopping quantities must preserve the ingredient's base unit and Shelf Life value/unit.
- [ ] `GET/POST /api/v1/recipes`, ingredient and `tblRecipeSupplies` CRUD endpoints, and validated waste-percentage updates per blueprint §9.2. Use `Decimal` for recipe quantities and costs; reject incompatible units unless a defined conversion exists.

## Feature 4.3 — Ingredient Cost History
- [ ] Feature complete
- [ ] `tblIngredientCostHistory`: ingredient, canonical `store_id` and its store item, effective date, purchased and normalized base units, normalized unit cost, currency, source purchase/receipt, and audit fields. Cost rows key by canonical store and store product identifier so grouped alias spellings roll up to one source history without merging genuinely different store products.
- [ ] Formula: `Effective Cost for Date D = latest Effective Date <= D` for the ingredient and its selected preferred vendor/location. Keep location on every cost row; if no preferred source is configured, label the selected latest-known source and surface that the default sourcing rule was used.
- [ ] This as-of-date resolution is the single authority for every financial calculation, report, and display, not only the cost-history screen. Any weekly or period figure — recipe cost, product cost, COGS, margin, profit, valuation, rankings, forecasts, tax workpapers — resolves each input cost as of the business date of the transaction or period being reported, never as of today and never from one global "current" cost. Worked example (D-57): a fruit cup of 1 cup + 3 strawberries + 4 watermelon pieces costs `0.10 + 0.40 + 0.10 = 0.60` in week 1; when week 2 receipts raise strawberries to `0.42` and watermelon to `0.12` while the cup has no new receipt and carries forward at `0.10`, week 2 costs `0.64`. Week 1 must still report `0.60` after week 2 is loaded.
- [ ] Carry a cost forward when a period has no new receipt for that input: the latest earlier effective row applies unchanged, and no value is invented from a later row, a sibling item, or a recipe. Mark a carried-forward cost in the UI and in export/drill-through with its effective date and source receipt/purchase so a reader can tell a carried-forward `0.10` cup from one confirmed by a receipt inside the reported period, and keep the existing `REVIEW COST` ageing signal (Feature 4.4) visible alongside it.
- [ ] When no cost row exists on or before date D for an input — including when the only rows are dated later — return the typed blocked result defined by D-61 instead of a number, carrying the reason code, exception ID, item, and date, and raise it as an open D-25 issue. Publish no guessed, zero, or later-dated value and never substitute a sibling item's cost. Blocking is per figure: neighbouring items and periods that do resolve must still calculate, and any aggregate containing a blocked component is published as incomplete with its blocking list attached.
- [ ] Never edit historical cost rows — insert new effective-dated rows only.
- [ ] Allow a preferred purchase source to be configured per ingredient as a canonical `store_id` and optionally a specific store item; changing that preference affects prospective recipe-cost views and must not rewrite historical purchase or sale costs.

## Feature 4.4 — Product Cost Engine
- [ ] Feature complete
- [ ] `tblProductCosts`: persist derived effective-dated Variation-ID cost snapshots with the recipe version or direct canonical-item cost inputs that produced them; most recent valid derived snapshot on/before the calculation date wins. MVP 2 owns recipe-derived and direct-item cost calculation. Do not provide a manual Variation-ID cost override or any typed/provisional cost path; a missing input returns the D-61 blocked result. Correct prior sales only through an audited adjustment/restate action after MVP 3 acceptance.
- [ ] Keep two distinct cost answers and never substitute one for the other (D-57). The **as-of-date recipe/product cost** resolves each input through Feature 4.3 for the requested business date and drives planning, price/margin views, recipe-cost displays, and period reporting. The **posted COGS** of a specific sale or produced lot is the lot-based actual cost captured at posting under Capability 6.3 and Capability 14.1 and is not recomputed when a later purchase changes the as-of-date answer. Label which of the two any displayed figure is.
- [ ] A receipt approved late — after its own week, or in a later week — appends its cost rows at the receipt's own effective purchase date, not at the approval date, so the earlier period's as-of-date answer changes retroactively. If the affected period is still open, recompute it and its dependent figures automatically. If the period is already closed under Capability 6.1, append a linked restatement version recording actor, time, reason, and the superseding values, rebuild the affected and all downstream periods from the ledger, and retain the original close; never silently rewrite a published close or a posted COGS snapshot. The same rule applies to an audited correction of an already-approved receipt line.
- [ ] `Cost Review Status = REVIEW COST` when Effective Date older than `cost_review_threshold_days` setting (default 90) — Governance Rule 7.
- [ ] Recompute affected derived fields whenever `cost_review_threshold_days` or an ingredient/product cost changes (settings-driven re-derivation, Capability 9).
- [ ] Test the D-57 cases with synthetic data: a two-week fruit-cup recipe where week 1 resolves 0.60 and week 2 resolves 0.64 from an unchanged carried-forward cup plus repriced strawberries and watermelon; week 1 unchanged after week 2 loads; a backdated receipt approved in week 2 for a week 1 purchase recomputing an open week 1 and restating a closed one; and a missing-earlier-cost input blocking only its own figure. Track CS-001, CS-002, and CS-003 in [the test-case manifest](../test-case-manifest.csv); planned focused command once implemented: `docker compose run --rm test pytest tests/test_effective_dated_costing.py -q`.

## Feature 4.9 — Units & Conversions
- [ ] Feature complete
- [ ] Maintain a unit catalog in which every unit has exactly one dimension: count (each, pack, dozen), mass (oz, lb, g, kg), or volume (fl oz, pint, qt, gal). Store receipt-text aliases per unit (for example `pt`, `PT`, `pint`, `pints` → pint); alias matching is case-insensitive and exact, and fuzzy matches are suggestions only.
- [ ] Maintain a versioned global conversion registry for same-dimension factors only (1 qt = 2 pint, 1 lb = 16 oz, 1 dozen = 12 each). Global rules never convert between dimensions.
- [ ] Maintain effective-dated, owner-entered per-item conversions for cross-dimension factors and package composition on ingredients, products, and supplies (for example Strawberries: 1 pint ≈ 0.75 lb and 1 pint normally contains 12 strawberries; olives: 32 oz jar normally contains 30 olives). They are specific to each item because package contents vary by item and source. Mark expected piece counts and cross-dimension factors as estimates; changing one never rewrites previously posted quantities or costs.
- [ ] Normalize a purchase to the item base unit in this order: (1) purchased amount = package count × pack size in the pack unit; (2) stop if already the base unit; (3) apply a global same-dimension factor; (4) if the dimension still differs, apply the item's own conversion or expected package composition to derive an approximate piece count; (5) if no path exists, keep the line as a draft and block posting to cost/inventory. Let the reviewer add the missing item conversion inline. Store the as-bought amount/unit, expected piece count when applicable, base quantity, actual receipt price, normalized unit cost, and the conversion versions used. Price comes from the receipt and is never inferred from piece count.
- [ ] Keep quantities and conversion factors as exact `Decimal` values through the calculation and round only money/display values at posting. Show values derived from an item conversion as approximate (for example "≈2.25 lb").
- [ ] Cover the worked strawberry example (base unit lb, 1 pint ≈ 0.75 lb) with synthetic tests: `1 PT` qty 3 @ $4.99 → 2.25 lb, $6.65/lb; `1 QT` $6.49 → 1.50 lb, $4.33/lb; `2 LB` $5.98 → 2.00 lb, $2.99/lb; `16 OZ` $3.99 → 1.00 lb, $3.99/lb; no size → blocked. Also cover the "points" → pint suggestion, a missing item conversion, a reversed base unit (pint), and conversion-version changes. Track CO-001 in [the test-case manifest](../test-case-manifest.csv); planned focused command once implemented: `docker compose run --rm test pytest tests/test_unit_conversions.py -q`.
