# Capability 1: Receipt Capture & OCR Pipeline

- [ ] **Capability complete** (all features below checked)

Bounded context: `mbs/receipts/` (blueprint §3.1 #5, §6). Accepts uploaded receipt images/PDFs, runs OCR, extracts structured line items, deduplicates, classifies categories. Runs as an async Celery task so uploads don't block the API.

## Feature 1.1 — OCR Engine Selection & Setup
- [ ] Feature complete

**Current choice:** Use local **Tesseract + OpenCV** processing for the Receipt MVP release. During local S1-S8 development, the provider-neutral boundary may use deterministic mocked extraction; receipt images/PDFs stay on the app's host during real local OCR. Persist the raw extraction and normalized data in Postgres so normal viewing and reuse never rerun OCR. Validate the configured local adapter against synthetic receipt fixtures and route uncertain fields to manual review.

Keep the provider-neutral `OCREngine` interface. **Google Document AI Expense Parser** is a future optional provider, not an MVP dependency; enabling it requires separate privacy, region, cost, and retry-policy approvals.

- [ ] Implement `OCREngine` with Tesseract + OpenCV as the configured local MVP provider; test extraction against synthetic image/PDF fixtures and flag uncertain fields for review.
- [ ] Include both selectable-text and image-only PDFs in the synthetic release fixtures; a PDF with a thin/empty text layer must still render its pages for local OCR. Retain page-level image/text provenance and send unreadable or conflicting rows to review rather than treating text-layer absence as an empty receipt (RM-023).
- [ ] Capture the local engine/version, raw extraction, confidence when available, and page count on the first successful processing; persist them before marking the job complete.

## Feature 1.2 — Upload & Async Processing
- [ ] Feature complete
- [ ] Define receipt PostgreSQL tables with SQLAlchemy 2 models and create or alter them only through reviewed, version-controlled Alembic migrations; do not apply manual DDL or use `Base.metadata.create_all()` to manage the schema. Test migrations against a fresh database and the prior schema.
- [ ] `POST /api/v1/receipts/upload` accepts image(s) or PDF, validates file type/size, stores to upload staging area, and creates the upload/outbox records (role: MANAGER+); a retrying publisher enqueues committed work to Celery.
- [ ] Support directory-selected batches through the same upload service, with independent validation, duplicate detection, protected storage, and job status for each file. Authenticated JPEG/PNG imports may proceed without malware scanning under D-09 after signature/size/dimension validation; PDF imports remain blocked for real-data use until scanning exists. An invalid, duplicate, or failed file must not discard successful files or prevent other valid files from processing; retries must not duplicate uploads or receipts.
- [ ] Bound batch file count, total bytes, and concurrent submissions with configurable limits enforced server-side as well as in the browser. Report limit failures explicitly; never silently truncate a directory selection. Treat browser-provided relative paths as untrusted display metadata, never as server filesystem paths or storage keys; identical filenames in different subfolders must not overwrite each other.
- [ ] Persist each staged file's upload row and an outbox/task event in one database transaction; a retrying dispatcher publishes committed jobs to Redis/Celery. Workers claim jobs with a lease/lock and idempotency key so a broker outage or worker crash cannot lose work or process one upload concurrently.
- [ ] Promote staged files to their immutable protected-store keys only after the upload record commits; clean abandoned staging files through an audited age-based janitor without deleting files referenced by live database rows.
- [ ] Enforce configurable maximum file bytes, PDF page count, image dimensions, batch count/total bytes, bounded concurrency, and allowed media types; do not impose a fixed uploads-per-hour limit. Verify file signatures (not only extensions), reject malformed/encrypted files, apply the approved JPEG/PNG no-scan exception, and keep PDF/source-file scanning behind future D-09 work.
- [ ] Compute a source-file SHA-256 and check it against `tbl_receipt_uploads` before enqueuing OCR. Reject/return the existing upload for an exact duplicate and do not rerun OCR; enforce a database unique constraint to handle concurrent duplicate requests.
- [ ] Make repeated confirmed directory submissions idempotent per source content, not filename or local path: unchanged bytes return the existing upload/job without OCR or another receipt. If a file at the same path changes (for example an image now shows five old orders plus five new ones), retain the original immutable source and accept the new bytes as a separate source version after validation and the applicable D-09 image/PDF policy. OCR the changed version and compare every extracted order to the canonical receipt identities; do not infer new orders merely from filename, page count, file hash, or item count. Audit the old/new source hashes and per-order existing/new/held outcomes (RM-025).
- [ ] Compute a local perceptual fingerprint for each image/PDF page before OCR. If it closely matches a stored source, mark the upload `POSSIBLE_DUPLICATE`, block OCR, and require a manager to confirm “already imported” or “process as a new receipt”; never silently override a possible duplicate.
- [ ] A near-match to an earlier snapshot of a changing image is a review hold, not proof that every contained order is old. After authorized resolution, process the new source version and deduplicate its extracted orders one by one; never discard new orders simply because most of the image matches an old snapshot (RM-025).
- [ ] Preserve each accepted PDF as an independent source with its own SHA-256, scan status, raw extraction, and page/line provenance. An order may span multiple PDFs, while two PDFs may overlap; after OCR, hold matching-order sources for manager copy-versus-supplement review instead of discarding different files solely because they resolve to the same receipt identity (Capability 2.1; RM-022).
- [ ] Process each newly accepted upload locally and persist the complete extraction before completing the job. Retry failed local jobs idempotently without creating duplicate receipt records; retain failure details and require manual review when extraction remains uncertain.
- [ ] Viewing, searching, correcting, exporting, or reloading a receipt must read saved database data and never call OCR. Rerun OCR only through an explicit audited ADMIN action that records the reason and saves a new extraction version without overwriting the original.
- [ ] Log engine/version, attempt, duration, failure reason, idempotent job key, and provider page count when applicable. Apply the configurable retention policy in Capability 2; if no period is configured, do not automatically purge source files or OCR payloads.
- [ ] Celery task orchestration per blueprint §6.3: (1) extract via configured OCR engine, (2) count existing `tbl_receipts` rows as pre-import baseline, (3) compute `Receipt_ID` per extracted receipt from the normalized printed store text (never the mutable canonical `store_id`) and check duplicates or supplemental-source candidates, (4) resolve the printed store to a canonical store, creating the store and alias when the normalized key is new and holding a missing/unreadable/multiply-matching value for review, (5) resolve each line to a store item by canonical store + store product identifier, creating the store item and, when no confirmed mapping exists, its canonical item, (6) classify each line item's category, (7) report existing/new/duplicate/source-attached/line-added counts separately, (8) create only new receipts or attach manager-approved supplemental lines to an existing receipt without replaying prior lines or approvals, (9) stamp `import_timestamp`.
- [ ] Task status/result endpoint so the UI can poll and show progress on the upload page.

## Feature 1.3 — Duplicate Detection
- [ ] Feature complete
- [ ] Define composite `Receipt_ID` key exactly as specified in blueprint §6.2/§4.2 (store + date + time + TC#/Receipt# derived key).
- [ ] Enforce `Receipt_ID` uniqueness in Postgres after OCR so each accepted order has one canonical receipt row. Compute its store component from the normalized printed store text so a later store rename, grouping, or split never re-keys an accepted receipt. If a different source resolves to an existing identity, retain it as a review candidate rather than inserting another receipt or overwriting accepted data; audit the decision to discard an overlapping copy or attach an additional source. When a partial PDF omits the receipt time, use reviewed store + purchase date + order number (and location when available) only as a provisional correlation key; conflicting or ambiguous headers must remain on hold, not be silently joined (RM-005; RM-022).
- [ ] Segment a source image or PDF containing multiple complete orders into independently reviewable order candidates with source/page/region provenance. Under a transaction/unique-key constraint, accept only genuinely new order identities, link pre-existing orders as evidence without replaying lines or approvals, and hold ambiguous or incomplete identities for manager review. One unresolvable order must not erase or duplicate the other valid orders in the batch; rerunning any earlier or later source version must leave the canonical order and line counts unchanged (RM-025).

## Feature 1.4 — OCR Data Field Extraction
- [ ] Feature complete
- [ ] Preserve the provider's raw Date and Time values in the OCR payload, then normalize the canonical receipt date to ISO 8601 `YYYY-MM-DD` and the canonical receipt time to `HH:MM:SS`. Ambiguous, incomplete, or invalid source values require manual review and cannot be posted as business dates.
- [ ] Extract required header fields: Store, Date, Time, TC#/Receipt#, Total. *(Unchecked 2026-09-30: RM-002 is `PLANNED` and the real Tesseract/OpenCV adapter is not integrated; the mocked boundary is component evidence only.)*
- [ ] Extract the printed store value, its normalized key, and any printed address/phone/location identifiers as distinct fields, and record the canonical store resolved by the Feature 1.2 orchestration step together with the matched alias. The raw printed store text is immutable evidence: it is never rewritten when a display name, grouping, or split changes later, and a user is never asked to type a store name for an imported receipt (ST-001).
- [ ] Hold a store value that is missing, unreadable, or matches more than one canonical store for review instead of guessing or creating a near-duplicate store; the held receipt still persists its raw extraction.
- [ ] Extract optional header fields: Subtotal, Tax, Payment Method. *(Unchecked 2026-09-30 with the required-field step above; RM-002 is `PLANNED`.)*
- [ ] Preserve printed order number, register/TR#, provider receipt ID, and payment REF as distinct candidate references. Choose the canonical transaction reference by a reviewed vendor-specific rule (for example, a Walmart REF may be chosen), retaining alternatives in raw OCR. Record card brand and last four only when actually visible, never infer fully masked digits, and avoid storing a full payment account number. Resolve ambiguous source timestamps in review rather than silently choosing a print/footer time (RM-022).
- [ ] Extract line items: Item Description (required), Line Total (required), UPC, Qty, Weight (lb), Unit Price (all optional per source formatting). *(Unchecked 2026-09-30 with the header-field steps above; RM-002 is `PLANNED`.)*
- [ ] Extract a printed merchant item number separately from UPC when present; the same description with a different item number is a different product, while repeated occurrences of the same item number may still be separate purchased lines. Retain source-file/page/line position so overlap review does not collapse valid repeats (RM-022).
- [ ] Treat the printed merchant item number (or SKU, or the provider variation ID for an imported provider order) as the store's product identifier, extracted as its own field and used by the Feature 1.2 orchestration step to resolve or create the store item keyed by canonical store + that identifier, with the printed description as its initial display name. Never key a purchased line, cost, or stock effect by description or common name. A line whose store product identifier is absent, unreadable, or conflicting is held for reviewer entry rather than matched by text (IT-001).
- [ ] Extract printed pack size and unit text when present (for example `1 PT`, `2 LB`, `16 OZ`) into raw line fields, separate from the purchased-package quantity. Never guess a missing size; leave it blank for reviewer entry (Capability 2.5; RM-021).
- [ ] Keep printed package size distinct from weighed purchase amount (`weight_lb`) and counted quantity. Do not infer unprinted sizes or units as OCR facts; optional business knowledge belongs in a separately reviewed annotation (RM-021; RM-022).
- [ ] Validate extracted totals against sum of line totals; flag mismatches for manual review rather than silently accepting bad data. *(Unchecked 2026-09-30: RM-009 is `PLANNED` and the go/no-go slice mapping lists the totals check as remaining from queue row S5.)*

## Feature 1.6 — Embedded Product Image Extraction
- [ ] Feature complete
- [ ] Extract raster images embedded in a source order/receipt document during OCR and retain each with its source file, page, and region provenance, its natural pixel dimensions, and its SHA-256. E-receipt and online-order PDFs commonly embed a product thumbnail beside each line; scanned paper receipts embed none, and that is a normal result, not a failure.
- [ ] Associate each extracted image with the receipt line whose region it occupies, using the same page/line provenance already recorded for line items. An image that cannot be associated with exactly one line is retained as unassigned evidence for reviewer attachment; never spread one image across several lines.
- [ ] Exclude non-product imagery before proposing a candidate: store logos and letterheads, barcodes and QR codes, decorative rules/separators, and any image smaller than `receipt_image_min_dimension_px` on either side. Never propose the rendered receipt page, a photo of a paper receipt, or a full-page scan as a product image (D-42).
- [ ] Hand every surviving image to the Capability 2.9 media-asset service, which deduplicates by SHA-256 and then perceptual hash so a repeated upload, a second source version, or two stores printing the same manufacturer thumbnail reuse one stored asset. Extraction never attaches an image to an item on its own; it creates a PENDING candidate that Capability 2.5 review must confirm or reject. If the item already has a confirmed primary image, confirming the candidate triggers the Capability 2.9 replace prompt (default No).
- [ ] Apply media-type signature verification and size/dimension limits to extracted images as to uploaded files. Extracted image candidates may proceed without malware scanning under D-09; record their unscanned status and provenance. PDF/source-file scanning remains a future real-data gate.
- [ ] Gate extraction behind the `receipt_image_extraction_enabled` setting. Extracted images are receipt-derived data: they inherit the receipt's data classification, retention policy, and legal/operational holds (D-15), and a purge removes them with their source receipt.
- [ ] Rerunning OCR must not duplicate assets, resurrect a rejected candidate, or alter an already-confirmed item image; re-extraction reuses existing assets and records a new candidate only for a genuinely new image. Cover IM-001 in [the test-case manifest](../test-case-manifest.csv); planned focused command once implemented: `uv run --frozen pytest tests/test_item_images.py -q`.
