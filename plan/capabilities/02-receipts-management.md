# Capability 2: Receipts Management

- [ ] **Capability complete** (all features below checked)

Covers storage and lifecycle of receipts once captured by Capability 1 — listing, retrieval, line-item detail, soft-delete, and the audit trail, plus the canonical store registry, the store-item-to-item mapping that give purchases a stable identity, and the shared media-asset store behind item imagery. Data model: `tbl_receipts` (summary) and `tbl_receipt_items` (line items), per blueprint §4.2. **Early Receipt MVP:** Features 2.1–2.9 are in scope, including dispositions, remembered item rules, store management, item mapping, and item images; they use thin receipt-linked review/business records and minimal ingredient/recipe links, not full stocked items without Shelf Life, later costing, inventory, or asset-depreciation modules (D-20).

## Feature 2.1 — Data Model
- [ ] Feature complete
- [ ] Create `tbl_receipt_uploads` as the file/job-level record: unique source SHA-256, protected file-store key, media type/size, uploaded_by/time, processing status, exact/perceptual duplicate status, OCR attempt/version/page count, and audit fields. A PDF containing multiple receipts may link to multiple `tbl_receipts` rows.
- [ ] Support the inverse relationship as well: one canonical `tbl_receipts` row may link to multiple source uploads/pages through a provenance association. Preserve each file's immutable extraction and its copy/supplement/rejected decision; add the necessary reviewed Alembic migration rather than replacing the existing upload FK in place. Corrections to the combined receipt must not rewrite any source extraction (RM-022).
- [ ] Model each accepted order occurrence from an image/PDF as a source-linked extraction candidate: one immutable source version may yield several distinct canonical receipts, and later versions of that image may link to those same receipts plus newly accepted orders. Persist the source checksum, original display path as untrusted metadata, page/region or line provenance, reviewed identity and per-order accept/existing/held state; a filename is not an idempotency key. Enforce uniqueness and transactional per-order acceptance under concurrent or retried batches without overwriting earlier extraction evidence (RM-025).
- [ ] Give each receipt an immutable UUID `receipt_pk` primary key for all relationships and API routes. Store the source-derived composite `Receipt_ID` as a separate unique deduplication key; corrections to OCR header fields never change the primary key or silently re-key an accepted receipt.
- [ ] If a corrected header would produce a `Receipt_ID` already owned by another receipt, hold the correction for explicit ADMIN duplicate/merge resolution; never overwrite either receipt or reassign child rows automatically.
- [ ] Create `tbl_receipts` with canonical queryable header columns (Store, Date, Time, TC#/Receipt#, Subtotal, Tax, Total, Payment Method), upload FK/page reference, import/review state, OCR provider/schema version, immutable full original OCR response as PostgreSQL JSONB (`raw_ocr_document`), versioned canonical receipt JSONB (`receipt_document`) containing accepted header plus line items/provenance/review state, reviewed_by/reviewed_at, and deleted_at (nullable, soft-delete).
- [ ] Create normalized `tbl_receipt_items` rows FK'd to `receipt_pk` as the canonical queryable line items, with Item Description, UPC, Qty, Weight, Unit Price, Line Total, merchandise Category, business disposition, OCR confidence, remembered-rule reference, and links to approved business records. Preserve unmodeled provider fields per line in a JSONB column (`raw_ocr_item`).
- [ ] Give each accepted item occurrence its own immutable receipt-line identity and source-file/page/line provenance. Keep merchant item number distinct from UPC; identical descriptions or item numbers do not by themselves prove duplicate purchase lines. Merging a supplementary PDF must retain repeated purchased occurrences without double-counting overlapping full copies or reposting prior approvals (RM-022).
- [ ] Capture package composition separately from price: a receipt line may be purchased as a package by weight or volume while the item master stores an effective-dated expected piece count for use in recipes and inventory estimates. Examples include a 1-pint strawberry container with an expected count and a 32 oz olive jar with an expected 30 olives. Expected counts are approximate conversions, not receipt facts; preserve the actual package amount, unit, and price from the source.
- [ ] Do not store the receipt image/PDF as a base64 string or large database blob. Store the original file in protected persistent file/object storage and retain its key, checksum, media type, size, and retention status in Postgres. The complete OCR document and extracted structured data remain in the database as JSONB plus normalized rows.
- [ ] Keep normalized header/item records authoritative for edits and business queries; update the canonical `receipt_document` snapshot transactionally with those rows, persist corrections/reviewer identity, and retain `raw_ocr_document` unchanged for audit and reprocessing. "Versioned" means a `receipt_document_version` counter plus retained prior snapshots, and every correction appends an immutable `tbl_receipt_corrections` event with actor, required reason, timestamp, before/after values, and an idempotent source event; overwriting `reviewed_by`/`reviewed_at` alone is not an audit trail (D-45, R2, RM-027).
- [ ] Store `raw_ocr_document`, `receipt_document`, and `raw_ocr_item` as PostgreSQL `JSONB` (SQLite variant allowed only in unit fixtures), and populate per-line `ocr_confidence` and `raw_ocr_item` from the extraction result or remove them until the extractor supplies them (R3).
- [ ] Provide the ADMIN resolution path for `Receipt_ID` correction holds (keep existing, re-key with reason, or reject) and convert a concurrent unique-constraint violation into a hold rather than an error; a hold with no resolution path is not a control (R2, RM-013).
- [ ] Create `tbl_stores` as the canonical purchase-source registry: immutable UUID `store_id`, user-editable `display_name`, optional merchant/chain identifiers, location fields, active status, and audit fields. Create `tbl_store_aliases` with the normalized source spelling, the raw printed/provider store text, source type, `store_id` FK, first/last seen, and the actor who grouped it; enforce uniqueness on the normalized alias so one spelling resolves to exactly one canonical store.
- [ ] Create stores and aliases automatically during order/receipt import from the store value read on the source document. A canonical store is never created from a typed purchase-form field, and a receipt keeps its matched `store_id` plus its raw store text so later renaming or grouping cannot alter the source evidence.
- [ ] Create `tbl_store_items` keyed by canonical purchase `store_id` + that store's `store_product_id` (merchant item number/SKU), with a database unique constraint, printed descriptions, optional UPC/common name, canonical `item_id` FK, mapping source, and audit fields. Square Variation IDs are sellable-product keys, not purchased store-item keys (D-52). A store item's description change never re-keys it.
- [ ] Create `tbl_items` as the application-wide canonical purchased-item identity: immutable UUID `item_id`, user-entered `common_name`, optional canonical description, item kind, active status, and audit fields. Every store item maps to exactly one `item_id`. An item first observed from a store always retains at least one store item and its last store item cannot be moved away (use an audited merge instead); an item created during master-data setup before any purchase may have no store item until its first purchase. Costs, stock, recipes, and analytics key by `item_id`, never by description or common name.
- [ ] Store the displayed item name as a derived value: use the store item's or item's `common_name` when present, otherwise the description read from the order. Persist the raw printed description unchanged and never promote a common name into an identity, dedup key, or match key.
- [ ] Link each `tbl_receipt_items` row to its `store_id`, `store_item` identity, and resolved `item_id`, and preserve those resolutions on posted purchase, cost, stock, expense, and asset records. Regrouping a store or remapping a store item is an audited, effective-dated change that does not rewrite already-posted records.
- [ ] Keep the store component of `Receipt_ID` on the normalized printed store text rather than `store_id`, so a later rename, grouping, or split cannot re-key an accepted receipt (D-10, D-37).
- [ ] Add `store_id` to `tbl_receipts` and `store_item`/`item_id` to `tbl_receipt_items` through reviewed migrations without a data backfill: the application has not been delivered and holds no receipts (D-10 clarification, 2026-09-30). Each migration must stop with a clear error rather than guess if the table already contains rows. Test the upgrade against the prior schema and a fresh database, and provide a tested downgrade path.
- [ ] Alembic migration(s) for the store, alias, store-item, and item tables with indexes on the normalized alias, `store_id` + `store_product_id`, and `item_id`, plus the receipt-item foreign keys.
- [ ] Create `tbl_media_assets` as the single content-addressed image store: immutable UUID `media_asset_id`, SHA-256 content key, protected file-store key, media type, byte size, pixel width/height, perceptual hash, derived-thumbnail key, scan status (`NOT_SCANNED` for the approved image exception), `origin` (`RECEIPT_EXTRACTED`, `USER_UPLOADED` for upload/camera capture), origin metadata JSONB (source upload/page/region for extraction), created_by/at, and retention status. Do not add an `AI_GENERATED` origin or generation metadata in MVP 1–8 (D-44). JPEG/PNG images may use D-09's approved no-scan exception after signature/size/dimension checks; PDF/source-file scanning remains a future real-data gate. Enforce uniqueness on the content key so one image is stored once no matter how many receipts, items, or recipes reference it. Image bytes live in protected file storage, never as a database blob or base64 string.
- [ ] Create `tbl_media_asset_links` as the audited attachment record: `media_asset_id`, owner type (`ITEM`, `STORE_ITEM`, `PRODUCT`, `INGREDIENT`, `SUPPLY`, `RECIPE`, `RECEIPT_ITEM_CANDIDATE`), owner ID, `is_primary`, display order, state (`PENDING`, `CONFIRMED`, `REJECTED`, `DETACHED`), actor, timestamp, and reason. Enforce at most one active primary per owner with a partial unique index, and keep detach display-only so the asset, its provenance, and any posted record that referenced it survive.
- [ ] Alembic migration(s) for the media asset and link tables with indexes on the content key, perceptual hash, and owner type + owner ID; images are display metadata and must never appear in an identity, deduplication, or matching key.
- [ ] Alembic migration(s) for both tables with appropriate indexes (Store+Date for filtering, Receipt_ID for dedup lookups).
